## Privileged receipt writer — internal only

\`lib/supabase-receipt-writer.ts\` is an explicit server-only adapter for the final **privileged metadata insert** in the \`ingestVerifiedEvidence()\` flow. The writer sends only five allowlisted, validated receipt fields to the fixed BidMason PostgREST table, using a server-owned **\`sb_secret_\` API key** in the \`apikey\` header. It does not transmit the requester's JWT as the privileged Authorization header, accept caller-selected endpoints, upsert conflicting records or return provider error bodies. Its expected organization is fixed at construction, and a missing/non-secret key disables it.

**Important security boundary:** The writer alone does not prove an uploaded document matches Storage bytes, validate active Auth sessions, authorize a tenant, or verify business claims. It must be constructed exclusively inside a protected backend operation, passed as \`issueTrustedReceipt\` to \`ingestVerifiedEvidence()\`, and invoked only after verified user Auth, tenant membership, insert-only private upload, exact byte readback and second membership check. A frontend or public API must never receive this callback or \`sb_secret_\` credentials.

This is **not deployed or configured**, and tests use a mock HTTP transport. Before exposing a real upload endpoint, implement trusted backend session transport, rate limiting, deny-by-default tenancy, actual Supabase upload/readback with two real users, orphan cleanup, document safety checks and key custody through secret deployment configuration. Privileged receipt inserts are not customer account privileges. No real credentials or customer records are stored in GitHub.

The complete **internal-only** operation is in [TRUSTED_EVIDENCE_SERVICE.md](TRUSTED_EVIDENCE_SERVICE.md). It verifies the Supabase Auth identity and current organization membership before constructing the trusted writer. The writer itself is not a standalone API or proof of the underlying Storage object.
