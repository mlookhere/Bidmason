# Item 3 → Item 4 real-schema compatibility gate (CI only)

Item 4's existing mandatory \`intake-db\` job intentionally uses \`ci/db_intake_stub.sql\`, a very small stand-in for \`bm_organizations\` and \`bm_memberships\`. It is essential for deep isolated correction and deterministic pricing tests, but cannot by itself establish that Item 4 can coexist with Item 3's **actual** tenant RLS schema.

The separately required \`item3-intake-compat\` Actions job checks out the existing Item 3 dependency branch \`work/4-tenant-rls\` and **fails closed unless its actual HEAD remains \`d17844b6387ffe9b5970dda1350a871276b38f7a\`**. This exact-SHA guard is deliberate: when Item 3 changes, review the changed dependency and update this expected SHA explicitly rather than silently accepting drift. It does not create or merge any Issue/PR or copy/replace Item 3 source.

It provisions its OWN isolated PostgreSQL 17 service, without real credentials, runs the dependency's \`ci/db_auth_stub.sql\` and **\`db/schema.sql\`**, then installs Item 4's \`db/typed_note_foundation.sql\` against those real table definitions and RLS policies. \`ci/db_item3_real_tenant_compat_test.sql\` requires all six real Item 3 tenant/business tables, enabled RLS, the three declared tenant read policies, FORCE RLS on Item 4's typed-note tables, no direct browser private intake permissions, and no self-promotion through membership writes. Finally, the existing adversarial Item 4 \`ci/db_intake_test.sql\` runs its cross-tenant denial, idempotent replay, duplicate-payload, immutable-source and revocation tests **against the real Item 3 schema**. The compatibility job runs Item 3's actual \`ci/db_rls_test.sql\` **immediately after the Item 4 schema is installed**, before Item 4's intake fixture adds its own users. This preserves Item 3's genuine fixed-membership assumptions: its Tenant B owner uses actor \`cccc...\`, whom Item 4's fixture also legitimately adds to its distinct synthetic organization. Executing Item 3's fixed-count tests after Item 4 seeds that second legitimate membership would produce a fixture collision, not a real RLS breach.

Next, the complete Item 4 \`ci/db_intake_test.sql\` runs against the real Item 3 schema. Finally, \`ci/db_item3_post_intake_rls_audit.sql\` **rechecks the combined RLS behavior after both suites**: the shared test actor sees only its TWO explicitly authorized organizations, never Item 3 Tenant A's facts or approvals, and cannot access private Item 4 source; Item 3 Tenant A's owner and contractor retain their respective scoped views, stale-brief rejection and unauthenticated denial. This proves both directions of compatibility without changing either component's original test semantics.

This job is a strict additional required check. A failure blocks promotion of the Item 4 branch and should be corrected by cause; never substitute the stub, delete tests, treat a missing job as green, or merge either draft PR without approved prerequisites.

**Limits:** This verifies Item 3 table/RLS compatibility in disposable PostgreSQL only, not Supabase Auth's live JWT and session lifecycle, two real users, Storage HTTP policies, signed upload scanning, ratecards, customer approvals, or production deployment. Existing Item 3 PR #12 and Item 4 PR #13 remain independent draft PRs into \`dev\`. Live Supabase Item 4 deployment preflight remains separately blocked until reviewed migrations and real two-tenant security acceptance.


## Full correction and pricing migration compatibility

The combined-schema job additionally installs **every remaining staged Item 4 SQL migration** in its dependency order on the authentic pinned Item 3 tables: extraction lookup/commit/read, reviewed policy activation and history, human scope and fingerprints, quarantine/draft/evidence/activation, corrected scope/commercial decisions, session-row verifier and locked pricing. The helper \`ci/install_item4_on_item3_disposable.sh\` rejects execution unless the CI-only disposable-PostgreSQL flag is explicitly set, and the connection points to \`127.0.0.1:5432\` as local \`postgres\` against the \`postgres\` database. It uses a **synthetic** Auth table created by the existing negative Auth session test; it must never be run on a connected live Supabase project.

After complete installation, the **existing required** 24-check \`ci/corrected_pricing_schema_preflight.test.mjs\` executes against that combined schema and must pass all security privileges, hardened functions, and rollback-only drift tests. It then reruns the post-intake Item 3 RLS audit **after all Item 4 SQL objects have been installed**, ensuring the later policy/correction functions did not silently alter tenant visibility. These are **three additional mandatory CI steps**; none of the original Item 3/4 tests or required jobs are dropped.

A success is evidence of staged schema integration against Item 3's real database definitions on disposable PostgreSQL only. It is **not** evidence of production Auth signatures, real users, private Storage HTTP permissions or approval to deploy. The last connected live Supabase readiness preflight must continue to report its own observed status separately.

### Preserving the real Item 3 Auth UID permission

Item 3's isolated `ci/db_auth_stub.sql` grants the `authenticated` role **USAGE** on schema `auth` and permission to execute `auth.uid()`, which its own security-invoker RLS policies use. The Item 4 synthetic `ci/db_auth_session_revocation_test.sql` temporarily revokes all `auth` schema usage to demonstrate session-table isolation, so running it unchanged in the combined database would also inadvertently hide Item 3's `auth.uid()` from its legitimate browser role. After that disposable test, the combined installer now restores **only** `GRANT USAGE ON SCHEMA auth TO authenticated`. It checks that `auth.uid()` is executable while `auth.sessions` remains unreadable to `authenticated`, `anon`, and `service_role`. It does not grant table privileges, change an RLS policy, or modify live Supabase, and the final tenant-isolation audit still runs in the restricted role. This corrects a fixture setup conflict rather than relaxing the Auth-session security guard.
