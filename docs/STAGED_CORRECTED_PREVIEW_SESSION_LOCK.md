# Session-locked corrected economics read (staged only)

`db/staged_corrected_preview_session_lock.sql` defines a private, service-role-only PostgreSQL function `bm_intake_private.read_corrected_internal_preview_session_locked(org, actor, session, source, decision_sha)`. It verifies the real `auth.sessions` session UUID belongs to the Auth-verified actor **and locks that row `FOR SHARE` in the same statement** before invoking the existing private source, company-member and active-policy checked projection.

The shared row lock prevents a concurrent session deletion from *completing* while the private preview is assembled; if sign-out already committed, the preview is denied. This is narrower than the earlier two separately committed Auth session probes. It does **not** lock or authorize later customer sends and cannot imply a customer offer or final approval. The corrected source remains revision 5 with prior `scope_review=NULL`.

The trusted server is responsible for independently validating the exact JWT with Supabase Auth, verifying its `sub` and signed `session_id`, and passing only those verified IDs to this function over a private primary database connection. **Never call this SQL function directly with browser actor/session IDs.** Browser roles have no EXECUTE grant, and the `service_role` still has no direct SELECT grant to `auth.sessions`.

This staged SQL does not create `auth.sessions` or change live Supabase schema, Auth configuration or session records. The mandatory disposable PostgreSQL fixture `ci/db_corrected_preview_session_lock_test.sql` asserts revoked-row denial, cross-user/tenant/source and forged decision rejection, positive private-only source-bound projection, and a second rejection after synthetic sign-out. A separate **session-bound TypeScript factory** now calls this SQL projection with the Auth-validated user and session IDs. The original four-argument SQL projection remains for compatibility with earlier staged tests. See `docs/STAGED_CORRECTED_SESSION_LOCK_ADAPTER.md`. No quote, delivery, deployment, merge or live security acceptance is authorized.

## Concurrency proof in disposable PostgreSQL

`ci/intake_session_lock_concurrency.test.mjs` exercises the real five-argument `read_corrected_internal_preview_session_locked` with **two concurrent PostgreSQL connections** after the SQL-level legacy bypass has been sealed. One `service_role` transaction reads the existing synthetic approved corrected-pricing preview, acquires the actual `auth.sessions` row lock, then holds the transaction open. A second connection attempts an Auth sign-out `DELETE` with a short PostgreSQL `lock_timeout` and **must fail specifically due to the row lock**, not an unrelated SQL exception. After the first transaction ends, session deletion must succeed and a repeated pricing read must fail because the session is gone.

This is a dedicated, mandatory `intake-db` job step. The test refuses to run unless `BIDMASON_CI_DISPOSABLE_POSTGRES=1` and all connection settings identify the isolated local Postgres instance. It does not open a live Supabase connection, alter customer sessions, or prove transactional authorization for any future pricing write or customer send.
