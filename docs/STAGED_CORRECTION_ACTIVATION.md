# Staged correction activation to renewed human scope review (Item 4)

A reviewed correction may advance from quarantine **revision 4** to **revision 5** only through the server-only `bm_intake_private.activate_reviewed_correction` transaction. Revision 5 means **awaiting an entirely new human scope review**, NOT approved quoting, delivery, or commercial policy. Original provider review/audit are never overwritten. The corrected candidate list remains in a private immutable table. Prior scope remains `NULL`.

Authorization requires a current tenant owner/operator who **independently accepted** the evidence and is distinct from the original creator. Creator membership must remain current. SQL locks membership and source, private hold, draft and accepted reviewer receipt, recomputes and checks source SHA, original and corrected candidate digests, complete reasoned action replay, original request hash, draft hash, and review hash. A private immutable one-time activation receipt is inserted atomically before advancing the source revision. The source's trigger refuses any revision 4→5 transition without an exactly matching private receipt, and rejects rewriting original evidence, correction hold, or scope.

Browser roles cannot invoke the activation function; neither browser roles nor `service_role` have direct insert, read or mutation grants to the private activation receipt. There are no legacy reader/writer code paths that accept correction revision 5 as quotable, and no new scope writer is part of this increment. **Never equate revision 5 with human-approved scope or economic approval.** Rejection, forged digests, self-activation, foreign tenant, revoked membership, missing review, duplicate activation and direct source/ledger mutation must fail closed.

This staging-only SQL needs separately independently verified Auth identities to safely be callable in an application. It is not a production migration or deployed feature. Item3 live Supabase Auth/RLS/private Storage, maintained malware scanning, legal/privacy/retention approval and a future completely new policy-bound corrected-scope review remain mandatory. See `ci/db_intake_correction_activation_test.sql` for disposable real PostgreSQL acceptance/denial coverage.
