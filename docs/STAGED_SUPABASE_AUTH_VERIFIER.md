# Staged Supabase Auth server verifier for private corrected pricing

This implementation adds `lib/supabase-active-session-verifier.ts`, an **opt-in** server-side `ActiveSessionVerifier` port. Live integrations must wrap it with `createSessionBoundSupabaseVerifier` and use the session-locked `createTrustedSessionLockedCorrectedEconomicsPreview` factory; the legacy four-argument preview factory is disabled in production. It does **not** configure a Supabase project, connect production, change database permissions, expose a public API or authorize customer sends. Source remains correction revision 5, with `scope_review=NULL` and a preview-only result.

The trusted server factory accepts an exact HTTPS project origin (`https://<project>.supabase.co`), a modern **`sb_publishable_` key only** and an optional injected HTTP transport used by tests. It rejects untrusted domains/ports/credentials/paths/query/fragment, service-role/secret keys, unbounded requests and malformed bearer access tokens. Each `verifyActiveSession` call performs a fresh `GET /auth/v1/user` with `Authorization: Bearer <access_token>` and `apikey`, no redirects, credentials or HTTP caching, and a bounded request timeout. It treats the Auth server's HTTP 200 JSON user UUID as the only identity proof, rejects anonymous users, and ignores caller-provided IDs, claims, user metadata and roles. Network, HTTP, JSON and token errors fail closed with a generic, non-secret message.

**Security nuance:** Supabase Auth's fresh `getUser`-style call confirms the currently valid JWT and user account but does **not promise immediate invalidation of previously issued access JWTs after server-side sign-out or session revocation**. The eventual production sensitive-operation gate must also verify the JWT's signed `session_id` against the current `auth.sessions` row (or an equivalent server-authoritative revocation source), use appropriate short JWT lifetimes, and test revocation against the real tenant. Existing private PostgreSQL methods separately re-check locked current tenant membership. This staged adapter never authorizes commercial release on its own.

**Integration path:** An authorized server handler would construct the verifier with trusted deployment configuration, wrap it in `createSessionBoundSupabaseVerifier` using a trusted primary PostgreSQL connection, pass that port and the connection to `createTrustedSessionLockedCorrectedEconomicsPreview`, and supply only the opaque access token in its `session` selector. The session-bound verifier obtains a signed `session_id` only after Auth verification and checks the current session record; the locked SQL reader confirms and locks that exact row. No credentials are stored in the repository and no live endpoint has been wired. Do not log or return raw Auth tokens, private policy snapshots, estimated direct costs or margins to clients.

The mandatory test suite `tests-web/supabase-active-session-verifier.test.mjs` uses a simulated Auth HTTP transport to check identity validation, two fresh checks, impersonation/metadata denial, malicious URL and header attempts, timeout/redirect/error failure, session expiry between SQL and calculation, and an internal-only 69,000-cent economic calculation through the combined adapter. This is **not live Supabase acceptance**; Item3 two-user Auth/RLS/private Storage and security/privacy/retention/legal requirements remain open.

## Bounded Auth response and absolute deadline

The Auth verifier uses a **single** `AbortSignal.timeout(timeoutMs)` for both HTTP headers **and** streaming the response. It rejects responses returned after that same deadline, even if a custom/mock transport ignores the AbortSignal. It validates the declared `Content-Length` when available but never trusts it as the actual length: streamed and decompressed `/auth/v1/user` JSON is hard-limited to **64 KiB**, including when the header omits the length or understates it. Invalid UTF-8, truncated JSON, zero-byte responses and non-JSON content types all fail closed. On a rejected stream, the reader is canceled best-effort. Tokens and provider responses never appear in exception messages.

The existing mandatory Node/Windows `tests-web/supabase-active-session-verifier.test.mjs` suite now covers accepted split UTF-8 chunks, the exact 64 KiB boundary, over-limit streaming despite a forged short `Content-Length`, invalid UTF-8, a body stalled after an HTTP 200, and a transport delivering HTTP 200 headers after deadline expiration. The test uses only injected HTTP responses; production Auth, credentials and real session revocation remain unverified.
