# Staged independent correction evidence review (Item 4)

The private SQL function `bm_intake_private.review_correction_evidence` records a **one-time, immutable decision about the evidence in a pending corrected-candidate draft**. It **does not** activate corrected candidates, alter the source's quarantine revision 4, approve scope, update a ratecard, create a quote, or send anything.

The trusted server must derive the reviewer and submitter from separately verified sessions. SQL locks and rechecks current tenant membership: the reviewer must be a current owner/operator; the original creator must remain a current member; they must be different people. Before any private source lookup, reviewer membership must pass. The function then locks the original quarantined source, draft, and correction-hold receipt and recomputes source, provider candidates, proposed candidate digest, action digest, source-bound request SHA and draft receipt SHA. It independently replays the human edits against the immutable provider extraction, requiring all evidence to match.

Permitted decisions are **`accept-evidence`** and **`reject-evidence`** only, with a bounded review explanation. They are *evidence review decisions*, not business approval or correction activation. Exactly one receipt may ever be recorded per source; wrong actor, wrong tenant, stale/forged digest, changed evidence, replay and direct browser/service table mutation are denied. Private evidence is never returned to browser roles.

The receipt is stored in `bm_intake_private.correction_evidence_reviews`, inaccessible for direct service-role/browser DML and protected by the existing immutable trigger. If approved evidence eventually moves toward activation, a **separate** durable transaction and independently audited tests must authorize that transition, invalidate all older scope, persist corrected lineage and require a **new** policy-bound scope review. A rejected correction needs a separate, designed re-submission protocol; do not silently overwrite these receipts.

`ci/db_intake_correction_evidence_review_test.sql` runs against real disposable PostgreSQL and proves two distinct member identities, self/nonmember/foreign-tenant/source/stale-hash denial, no direct writes, no replay, immutable evidence and continued quarantine without a commercial quote. This is not live two-user Supabase Auth/RLS/Storage integration; maintaining those gates and malware/retention, security, privacy and legal acceptance remains mandatory.
