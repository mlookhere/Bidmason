# Staged server-only Supabase Auth session binding

Supabase's published [user sessions](https://supabase.com/docs/guides/auth/sessions) documentation describes a UUID `session_id` claim in each access token that correlates with `auth.sessions.id`. An access JWT may remain cryptographically valid after sign-out; a fresh `/auth/v1/user` response alone does not enforce a strict immediate sign-out guarantee. On sign-out, the affected session row is removed.

**New server-side adapter:** `lib/supabase-session-bound-verifier.ts` wraps the existing `createSupabaseActiveSessionVerifier` and a server-held primary PostgreSQL connection. Each call first makes the trusted Auth server independently verify **the exact bearer token**. Only after successful Auth verification does it parse the JWT payload, require a matching `sub`, strictly valid UUID `session_id`, sensible `iat` and unexpired `exp`, then query the service-only database `bm_intake_private.auth_session_is_active(user_id, session_id)`. A missing or revoked row or user/session mismatch fails closed, even when the JWT remains otherwise accepted by the Auth API. The existing internal corrected economics adapter re-verifies this complete port before and after its database preview, with each verification issuing a fresh Auth request and session probe. Claims are *not cryptographically trusted by parsing*—trust comes only from the preceding successful Auth-server check.

**Staged database contract:** `db/staged_auth_session_presence.sql` creates only the service-role-only SECURITY DEFINER function, not the `auth.sessions` table. The function has a hardened search path and verifies both session primary key and owner UUID in `auth.sessions`, using a shared lock for its statement. Browser roles cannot call it or read session records. This is a proposed migration for a controlled server environment, **not** yet deployed to Supabase. All actual production schema grants, function owner, no-public-RPC exposure and real session/tenant concurrency behavior still need review.

**Disposable CI fixture:** `ci/db_auth_session_revocation_test.sql` creates a minimal synthetic `auth.sessions` in an isolated ephemeral PostgreSQL instance, verifies no browser/service direct-table read grant, positive current session, cross-user/foreign/missing/null denial, and rejection after the session row is deleted. `tests-web/supabase-session-bound-verifier.test.mjs` uses a trusted simulated Auth verification port to prove refusal of malformed/expired/mismatched JWT claims, revoked rows and Auth server errors. Neither fixture changes a live Supabase project.

**Hard production blockers:** Strict checks are as strong as the authoritative session row query at the time of each operation; revocation between a session probe and later operation is a normal time-of-check/time-of-use race. To guarantee atomic authorization for a sensitive *write*, require a transaction that locks the session and tenant membership and performs the write in that same transaction. No sensitive corrected-estimate write, public quote/send interface or final commercial release is enabled here. Live signed-token verification, real Supabase Auth/RLS/private Storage, AV/retention, privacy/legal/security and operational review remain incomplete.
