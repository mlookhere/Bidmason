# Evidence upload HTTP boundary — internal, not production enabled

**Status:** `lib/evidence-upload-boundary.ts` is a tested internal processor. There is **no public POST route**; the server-only quota and ClamAV adapters exist but are not deployed as a customer upload service. Customer-facing uploads remain disabled.

## Contract

`processEvidenceUpload(request, deps)` accepts only a raw PDF, PNG or JPEG body, a canonical `x-bidmason-organization` UUID, an explicit valid `Content-Length` from 1 byte to 15 MiB, and a Supabase Auth bearer token. Multipart, JSON/base64, URL-selected buckets/hosts, caller-supplied user IDs, and client-controlled secret keys are not supported.

1. **Fail closed before I/O:** real server-side `sb_publishable_` and `sb_secret_` keys, a distributed/durable quota callback and an independent malware-scanning callback must all be installed by a trusted server entrypoint. A missing dependency returns 503. A process-local JavaScript counter must not be used as the authoritative rate limit in multi-instance hosting.
2. **Authenticate before receiving file bytes:** reuse `lookupAccount()` against Supabase Auth with the user's JWT, then confirm an RLS-scoped membership in the exact requested tenant. An invalid or cross-tenant token cannot get to scanning or trusted receipt issuance.
3. **Reserve quota before reading:** a deny returns 429; quota-service errors block with 503. In addition to an authenticated per-user/tenant quota, the eventual ingress needs edge-level unauthenticated request-rate and body-size enforcement.
4. **Bound the stream by actual bytes and time:** require Content-Length, refuse unsafe lengths, read only to the declared size, cancel overflowing streams and reject truncation. `readExactEvidenceBytes()` enforces a nonconfigurable 30-second maximum at the production call site, rejects aborted/stalled clients with HTTP 408, and never waits on attacker-controlled cancellation promises. Signature-check PDF/PNG/JPEG magic bytes using `prepareEvidenceReceipt()` from the existing domain module.
5. **Mandatory scanner:** only the exact trusted response `clean` continues. A scan rejection or scanner fault prevents calling Storage. Signature checks are **not** malware checks and a synthetic clean callback is **never** a deployment-ready scanner.
6. **Trusted issuance after verification:** reuse `ingestForSignedInMember()`, which independently authenticates, checks user-scoped private upload/readback integrity, reauthorizes membership and creates a privileged immutable receipt. Provider errors never return success.

## 2026-10-18 bounded body deadline and cancellation hardening

`lib/bounded-evidence-stream.ts` handles the incoming request body with a **hard 30-second overall read ceiling** (not merely an idle timeout), observed client disconnects, exact streamed lengths and capped per-chunk handling. Aborted/stalled requests fail with 408 and **do not reach scanning or private Storage**. The hard deadline is not read from a header or tenant preference. Upload quota is reserved before body read and conservatively remains consumed if a client stalls. No unauthenticated edge throttling is implemented by this feature. `tests-web/bounded-evidence-stream.test.mjs` covers missing/short/excess body, stuck streams, aborts, exact size without EOF, nonbinary/empty chunks and invalid deadline parameters. All tests are offline simulations, not live customer HTTP traffic.

## 2026-10-18 fragmented-body and scan-time disconnect hardening

The exact body reader now preallocates at most the validated 15 MiB `Content-Length` and writes chunks into one fixed-size array, rather than keeping a new array for every network fragment. A fragmented 8,192-part binary body and post-read input mutation are regression-tested. An already disconnected client, or one whose signal aborts while malware scanning, cannot advance from a clean verdict to trusted evidence ingestion. The scanner may still need independent abort propagation to release its own daemon socket immediately; no production ingress or deployment is enabled by this code.

## 2026-10-18 preflight Auth and atomic quota cancellation

The server-owned `Request.signal` is now passed through the **initial** Supabase Auth/membership lookup and `bm_reserve_upload_quota` RPC, closing the last pre-file-read cancellation gap. A disconnect before these operations or while either is in flight produces 408 and refuses all downstream body reads/scans. The quota adapter combines the abort signal with the existing fixed seven-second timeout and never retries or refunds a reservation when the RPC response is ambiguous; a remote transaction can commit despite a disconnected caller. Adversarial tests verify pre-abort, held Auth, held quota, signal identity through server composition and quota success arriving after abort. These are offline tests, **not** genuine multi-user Storage or live service quota verification. No public upload endpoint was enabled.

## Critical server-managed Storage INSERT lockdown (2026-10-18)

**Security correction:** The earlier tenant-member `storage.objects` INSERT policy allowed a signed-in member to call Supabase Storage directly. Although it enforced tenant prefix and ownership, that bypassed the *application* scan and distributed quota because Storage cannot attest that a file was actually scanned. The additive `db/storage_insert_lockdown.sql` / `supabase/migrations/20261018100829_bidmason_scan_gate_storage_lockdown.sql` introduces a second **restrictive** RLS INSERT gate which excludes the entire `bm-evidence` bucket for non-bypass client roles. This gate remains effective even if another permissive INSERT policy is later added; it preserves existing private READ rules.

**Intentional consequence:** The legacy `createSupabaseEvidencePort().uploadPrivate()` uses the signed-in user's JWT and now **fails closed** against live Storage. The internal trusted ingestion service has been switched to the pinned server-managed write path, but this low-level function must never be published outside the already quota- and scan-gated internal boundary. No public POST route, direct signed URL grant, policy exception, hidden bypass or weakening of existing tests is allowed. Previous successful mocked upload tests only establish the pure service ordering, not deployability. Final-state CI checks require denial of direct owner/contractor INSERT and simulated permissive-policy bypass in **both** normal schema and actual migration replay. Live two-tenant Storage/Auth tests and production malware definitions still block enabling uploads.

## Internal privileged adapter wired behind quota and scanner (2026-10-18)

The trusted ingestion service now uses the server-managed Storage transport rather than the user-JWT writer (which the deployed restrictive Storage INSERT policy deliberately denies). This does not add or enable a customer upload POST. The internal `processEvidenceUpload()` must first authenticate user+tenant, atomically reserve quota before reading request bytes, enforce exact body bounds and magic bytes, and require explicit ClamAV `clean` before calling the trusted service. Privileged Storage receives `sb_secret_` only in the `apikey` header with a fixed project and tenant-scoped object key; user JWT remains restricted to Auth and membership queries. A previously-scanned-file boolean supplied by clients is never trusted. The server-managed low-level ingestion service **cannot** itself prove a scan and must remain internal. Contractor-specific read attribution is now backed by `uploaded_by` on immutable receipts and two updated private Storage SELECT policies in the dedicated test Supabase project; real two-user Auth/Storage API evidence remains outstanding. No public upload route or production readiness is claimed.

## Mandatory signed ClamAV readiness before production scanning (2026-10-18)

A local ClamAV daemon returning `stream: OK` does **not** establish that its loaded definitions are official, signed or current. The internal trusted-server factory now requires an absolute server-managed `clamavSignatureDirectory` and always composes `createProductionClamAvScanner()` in place of the raw INSTREAM-only scanner. **Before every scan**, the production wrapper locates a regular `daily.cld` or `daily.cvd`, runs local `sigtool --info` with a bounded timeout to require official signature verification and nontrivial signature count, rejects database build times older than **72 hours** or more than five minutes in the future, and calls the loopback-only `zVERSION` protocol to verify that the actual daemon has loaded the **same daily database version**. Scanner cancellation, bad/missing/tampered definitions, stale signatures, disabled VERSION, mismatch and timeouts are all fail-closed; only afterward can the exact local INSTREAM `clean` verdict permit ingestion. A test-only EICAR signature database cannot pass this production gate.

Offline tests cover parsers, unsigned/stale/future/mismatched responses, missing databases and abort. The isolated `av-real` CI continues to prove genuine engine detection using its *temporary test signature*, **not production vendor definitions**; do not treat parser mocks or EICAR-only CI as production readiness. Deployment still requires trusted freshclam updates, correct daemon database directory, current ClamAV engine patches, loopback firewall, secrets, monitoring and an explicit production operational check. No customer POST/download route is enabled.

## Bounded privileged quota decision response — 2026-10-18

The internal `bm_reserve_upload_quota` POST now **rejects unbounded or stalled provider response bodies**. Previously, its `Response.json()` accepted arbitrarily large or indefinitely streaming data after HTTP headers; a remote boolean result could be ambiguous on a client disconnect. The adapter now limits a PostgREST boolean response to **64 bytes**, validates any declared `Content-Length`, uses the shared fixed-buffer JSON reader, and applies one **7-second total HTTP + body** provider AbortSignal. Only a fully completed JSON boolean `true` grants a permit; an explicit `false` denies. A partial, malformed, oversized, aborted or unavailable reply always fails closed, without retry or quota refund: the atomic reservation may already have committed upstream. Negative tests cover response streaming after headers, client disconnect, accepted true/false, malformed and oversized bodies, suspicious length and no retries. **This is not a genuine privileged service-key RPC integration test and does not enable uploads.**

## Scan-to-ingestion byte identity (2026-10-18)

The internal upload processor now supplies the trusted malware scanner with a **separate copy** of the authenticated, bounded, MIME-validated bytes. Following a `clean` verdict it compares the entire scanned snapshot against the authoritative ingress bytes **before** invoking privileged Storage ingestion. If the scanner adapter modifies the bytes while claiming a clean scan, the upload fails closed with 503 and never calls Storage or receipt issuance. An explicit unsafe verdict still fails with 422. This prevents a scanner/plugin memory mutation or asynchronous buffer alteration from turning a verdict on one payload into persistence of a different payload. The source bytes cannot be changed via the scan callback, and the normal ingestion service independently snapshots the bytes for Storage and verifies readback hashes. Tests cover normal 201 success with distinct scanner/ingest buffers, synchronous and asynchronous mutation during a clean verdict, and unsafe mutation with no write. This remains an **internal-only** hardening; no customer upload endpoint is enabled and genuine production ClamAV/Supabase integration still requires approval.
